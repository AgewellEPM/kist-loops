# Kist / COBOL baseline — September 8, 2026

Kist's real SML-to-MCP path constructs runnable COBOL for the current template
families. The builder's `verified` label does not establish that the requested
behavior was delivered. This baseline found 12 failing case contracts, reproduced
in both repetitions; it is not an autonomous evolution acceptance result.

## Measured result

The full 101-case suite ran twice against a fixed copy of Kist 0.17.62 and the
actual configured COBOL MCP source. No mocked tool answers were used.

Eleven of 13 construction families passed every tested size. `count-over` passed
10/12; `vowel-count` passed 0/8. All other numeric families, ASCII digit counting,
and the fixed indexed-file write/read routine passed their finite test sets.

The campaign took 447.30 seconds. Successful MCP requests had p50 **0.142 s** and
p95 **0.211 s**; successful approval sessions had p50 **0.624 s** and p95 **0.731 s**.
These include recorder overhead and the machine's concurrent workload. They are
observations, not portable performance limits.

## Repair priorities

1. **Prevent incorrect verified substitutions.** `sum 7 positive values` returned
   `count-pos`: an all-positive input summed to 49 but produced 7. A request for
   both minimum and maximum returned a range. Parse explicit operations and either
   implement the full contract or refuse unsupported combinations.
2. **Parse size and threshold separately.** Size 1001 became 1, negative size -3
   became 3, and valid size 100 was removed along with the threshold literal 100.
   Validate the complete signed size token and its allowed range before composing.
3. **Make behavioral verification match the public contract.** Lowercase vowels
   produced zero, including a 999-character lowercase input expected to produce
   999. Add mixed-case and boundary tests to the builder's own verification.
4. **Improve supported intent recognition.** `min of 7` and `max of 7` were refused.
   Add token-aware aliases and keep the new negative/composite cases in regression.

After repair, rerun the unchanged suite and add separately authored held-out
examples before claiming a capability gain. Ledger, reconciliation, fixed-point
invoicing, and payroll programs should become separate benchmark sets with explicit
input layouts and golden outputs; the current reduction templates do not prove
those complete business workflows.
