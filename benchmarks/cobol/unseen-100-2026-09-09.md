# Kist / COBOL: 100 new local cases and paired rephrasing

Measured September 8–9, 2026. This is local executable benchmark evidence, not sealed Kist mission acceptance, production promotion, or proof of autonomous evolution.

The first round scored **56/100 with model interpretation** and **14/100 with the standalone deterministic builder**. Supplying the previous round did not increase the rephrased-round score over a fresh-context control. All unimplemented operations were refused. Refusals earn zero capability credit.

| Round: the same 100 task identities | Kist + model interpretation | Standalone COBOL builder |
|---|---:|---:|
| Original requests | 56/100 | 14/100 |
| Rephrased, with previous round available | 56/100 | 14/100 |
| Identical rephrased requests, fresh control | 56/100 | 14/100 |

Across all six conditions: **600 requests**, **210 independently compiled programs**, **3270 passing runtime checks**, and **390 refusals**. No returned executable failed these checks; there were no infrastructure errors in the scored rounds. Finite passing examples do not prove universal correctness.

## What was evaluated

The assisted route used a real Kist durable SML `CALL_MODEL`, bound to the configured `codex-cli:gpt-5.6-sol` provider, to interpret each raw request into the existing COBOL tool grammar. Each round was one batch of 100 requests. The model was given the complete 14-operation tool contract and told to preserve the full intent or copy an unsupported request unchanged. The returned requests then ran through real Kist `CALL_TOOL` dispatches and the repaired `cobol-build` MCP server. The model did not write arbitrary source or edit the tool. Therefore the 44 unsupported cases test the current tool path, not the maximum code-generation ability of the model or unrestricted Kist agent.

The standalone route called `cobol_build.cobol_build` from a byte-identical frozen copy of the same repaired builder. It did not invoke Kist, a model, an embedding system, or the optional neural routes elsewhere in the COBOL-SML repository. The Python worker blocked model imports, Python network access, and subprocesses other than the installed compiler and generated fixtures. Both worker proofs record zero network attempts, zero model-import attempts, and no loaded model libraries. The builder is Python orchestration that emits and executes COBOL; this is not a claim that the entire orchestration process is written in COBOL.

Every returned program was compiled again with installed GnuCOBOL and checked against host-side Python reference results. The oracle never imports the builder. Paired tasks use exactly the same runtime inputs and expected outputs in every condition where a program was returned.

## Novelty and test distribution

The frozen corpus contains 25 operation families at sizes 23, 47, 83, and 149: **56 instances of 14 existing families** and **44 instances of 11 unimplemented families**. These are 100 new local operation/size/wording/input combinations, not 100 novel algorithms. There were no exact prompt matches in the two previous benchmark manifests or the 2,298 rows scanned in four local training/test datasets. Absence from proprietary model pretraining cannot be established.

The unimplemented families were negative-only sums, even counts, odd counts, counts above 50, counts below −20, sums of squares, maximum absolute value, distinct-value counts, position-weighted sums, uppercase-letter counts, and space counts including fixed-width padding. Each had four cases and scored 0/4 in every condition. The system did not acquire a new operation during this run.

Original requests used canonical syntax, natural prose, embedded JSON, and worded sizes. Rephrasings used a multiline specification, canonical syntax, different prose with worded sizes, and a prefixed construction request. Rephrased IDs and order were independently shuffled; the evaluator retained the private pairing. Format and size are deliberately paired in this corpus, so format-specific results are descriptive rather than a fully crossed estimate of format effects.

Numeric routines received 18 runtime checks each, including sign, zero, strict-threshold, duplicate, fractional-average, seeded random, and permutation examples. Inputs stayed between −50 and 150 and expected results fit the declared ABI. Strings received nine checks, including lowercase vowels, uppercase vowels, padding, digits, and the final character. Indexed-file programs received two fresh-directory checks for exact ascending keys. These checks do not establish arbitrary database behavior or production business logic.

Before scoring, four harness tests passed, including a handwritten sum-of-squares program accepted by the oracle and a wrong plain-sum program rejected against that same new-operation contract. The corpus, oracle, builder, and other pinned execution files were not repaired or tuned after scoring began.

## What the memory comparison establishes

For the model-assisted warm round, the prompt included the original requests and the model’s previous normalizations. It did not include scores, expected outputs, evaluator labels, or the private task pairing. The cold round used the same model instructions and identical rephrased requests without this prior context. This measures explicitly supplied context reuse. It does not test native long-term Kist memory retrieval, training from corrections, or model-weight updates.

- **Assisted:** warm minus cold = 0 correct cases; 0 helped and 0 hurt by prior exposure. All 100/100 classifications matched between warm and cold.
- **Standalone:** warm minus cold = 0 correct cases; 0 helped and 0 hurt by prior exposure. All 100/100 classifications matched between warm and cold.

The standalone warm and cold runs returned identical full responses for **100/100** rephrased requests. The warm worker handled the original 100 and rephrased 100 in one process; the cold worker was a new process. Template metadata and function-code hashes were unchanged after every request.

The standalone original round solved the 14 canonical requests at size 23. After rephrasing, those 14 were refused and the 14 now-canonical size-47 requests were solved instead: zero cases were correct in both standalone rounds. The stable total of 14/100 masks a complete swap in which tasks passed. That is wording sensitivity, with no observed benefit from prior execution.

The assisted route already solved all 56 supported-family cases in the first round, leaving no headroom within that group. Its tool contract excluded inventing the remaining operations. Consequently, the zero warm/cold gain must not be generalized to “the model cannot remember” or “Kist memory is broken.” It shows no measured history benefit in this bounded pipeline and no capability expansion in the builder.

Each model condition was sampled once; this is not a statistical estimate across repeated stochastic model runs. The warm and cold model calls returned identical normalized request text for all 100 rephrased cases.

## Recorded execution and audit

The final audit reconciled 4685 process records and their stdout/stderr hashes, every score row against its saved case result, returned source against compiled source, executable hashes, all runtime observations against expected values, and identical oracle inputs across paired cases. It verified 300 actual MCP tool calls with exactly one dispatch each, 1200 matched MCP starts/stops, approval gating, stale-approval rejection, claim release, and no replay on restart. The standalone workers recorded 300 builder calls.

All **21 pinned files** still match their frozen hashes. The final process inspection found no remaining benchmark workers, Kist sessions, or frozen MCP servers. All four existing autonomy flags remain false. No production deployment, template learning, or unattended evolution was performed. The one failed authentication probe under the shell sandbox is preserved separately from the scored cases; the configured authenticated route then succeeded. Probe requests contained no corpus cases.

The assessed executable is the frozen Kist 0.17.62 CLI used by the prior repair campaign; these results do not silently substitute the concurrently changing `.build` binary or certify a different installed build. The MCP snapshot exactly matches the configured sidecar source, including its 1.1.0 server version.
